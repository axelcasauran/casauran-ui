# Stage F0.19: Documentation Interaction Foundation

Type: foundation
Status: complete
Completion date: 2026-08-15
Prompt: `.agent/prompts/foundation-stage.md`
Decision: `.agent/decisions/ADR-024-documentation-interaction-foundation.md`

## Objective

Give every component route a per-capability information architecture and a genuinely interactive
example harness, generated from a declared topic model so the shape holds across all 127 components
instead of being rebuilt per stage.

## Rationale and ownership decision

The `1.01 Button` revalidation on 2026-08-15 showed that documentation completeness and
documentation _experience_ are different problems. ADR-023 closed the completeness half: every
declared feature must be demonstrated, and enumerated features must preview every value. It cannot
close the other half, because the single-page route shape and the static example primitive are F0.18
contract clauses, and changing them affects every component route rather than any one component.

ADR-024 accepts F0.19 at the current ledger boundary after F0.18, following the ADR-020 precedent,
so the completed stage prefix stays truthful and `1.03` inherits the finished model rather than
being migrated afterwards.

## Scope

- A declared topic model naming the capability topics a component route may publish — overview,
  appearance, sizes, states, icons and content, events, forms, controlled state, keyboard,
  accessibility, globalization, performance, security, API, limitations — with required and optional
  topics distinguished.
- Route and nested-navigation generation from that model, replacing hand-authored single pages, with
  sidebar nesting and per-topic tables of contents.
- Migration of the existing Button and Icon routes with no content loss and continuity for published
  `/components/<slug>#section` deep links.
- An interactive example primitive: a narrow client island per example so toggles toggle and forms
  submit, with global theme, density and direction control left to the shell.
- One source of truth for example code, so displayed source is the code that renders or is
  mechanically verified against it.
- Extension of the ADR-023 coverage rule to resolve a feature's declared anchor against the topic
  that owns it.
- Browser and visual evidence for the new navigation, including keyboard and mobile behaviour, and a
  recorded hydration and bundle cost for the example islands.

## Dependencies

- Accepted ADRs 001, 003, 008, 009, 010, 013, 019, 020, 022, 023, 024, 999.
- Completed F0.18 documentation experience foundation.
- Existing supported `@casauran/react`, `@casauran/theme`, `@casauran/tokens`, and `@casauran/icons`
  exports only.

## Acceptance criteria

- Component documentation is reachable per capability topic, and the sidebar reflects the nesting.
- Routes and navigation are generated from the declared topic model; adding a component does not
  mean hand-writing topic pages.
- Every previously published component route and section anchor still resolves.
- Examples that demonstrate interactive behaviour are interactive, and their displayed source
  matches what renders.
- ADR-023 coverage still passes for every documented component under the new anchor resolution.
- Documentation client boundaries remain local example islands; route modules and the package root
  stay server-safe, and the validator describes the new allowed set rather than dropping the audit.
- Hydration and bundle cost of the example islands is measured and recorded.

## Boundary

Out of scope: per-example theme, density or direction switchers; a props playground; documentation
search; versioned documentation; any public component, token or API change; and any stage `1.03`
work. This stage ships no public component.

## Outcome

Outcome: COMPLETE

Completed: 2026-08-15. Component documentation is now generated from a declared topic model, and
examples are interactive with source read from the module that renders them. `1.03 SVGIcon` is next
and remains `not-started`.

## Delivered scope

- Governed topic model at `registry/documentation/topics.json` with its schema: seventeen ordered
  capability topics, three of them required (`overview`, `api`, `accessibility`).
- Generated routes: `/components/<slug>` publishes the overview plus a topic index, and
  `/components/<slug>/<topic>` is generated for every published topic through
  `generateStaticParams`. The build emits 23 component routes from two content declarations; adding
  a component means declaring topics, not authoring page files. A `/components` index route was
  added for the breadcrumb and library listing.
- Deep-link continuity: every section anchor published under the single-page model still resolves
  on the component overview and links to the topic that now owns it.
- Nested navigation: the sidebar lists each component with its topics, marks the current topic with
  `aria-current`, and keeps one skip link and one main landmark per page.
- Interactive examples: `ExampleFrame` is a client island per example with Example/View source tabs
  and roving `aria-selected` state. Four Button examples are genuinely interactive — cancellation,
  form submit and reset, controlled ownership, and pressed state.
- Verified example source: `readExampleSource` reads the example's own module at build time and
  `Example` has no `source` prop, so a hand-written string that disagrees with the preview is not
  discouraged but impossible.
- Coverage resolution: ADR-023 anchors now resolve against the topic that owns a feature, and
  enumerated values are searched across the content module and its example modules.
- Migration: Button's sixteen sections and Icon's six became topic pages with no content loss;
  Button publishes fifteen topics and Icon five.

## Validation

- `pnpm validate:documentation-experience` — PASS: 20 documentation capabilities, topic model,
  published topics, and feature coverage.
- `pnpm test:contracts` — PASS: 160 tests, including 15 documentation-coverage rejection tests.
- `pnpm test:unit` — PASS: 122 tests. `pnpm lint`, `pnpm format`, `pnpm typecheck` (workspaces,
  tests, tooling), `pnpm architecture` — PASS.
- `pnpm build` — PASS: 27 libraries and 4 production Next hosts; the documentation host emits 23
  generated component routes.
- Chromium browser suite for `tests/browser/docs-shell.spec.ts` — 5 behavioural checks PASS,
  covering SSR and deep-link continuity, registry metadata, generated topic navigation and paging,
  per-topic feature coverage against real markup, and an interactive example whose cancellation
  behaves and whose published source matches the module that renders it. The two visual cases
  regenerated their `chromium-linux` baselines, which were reviewed image by image; light desktop
  and dark/compact/RTL both render the nested topic navigation correctly.
- Firefox and WebKit could not be installed in this environment, so the three-engine gate and
  `pnpm validate` were not run to completion and are not claimed.
- Performance: recorded in `.agent/performance-budgets.md` — islands 15.1 KiB in their own chunk
  against a 32 KiB ceiling; topic route 185.3 KiB gzipped against a 256 KiB ceiling.

## Enterprise applicability

- Functionality and API: pass — routes, navigation, metadata and tables of contents all derive from
  one declaration; no public package or component API changed.
- Accessibility: pass — one main landmark and one `h1` per topic route, `aria-current` on the
  active topic, tab semantics with `aria-selected` and `aria-controls` on example views, the skip
  link and mobile navigation unchanged and re-proven.
- Keyboard and input: pass — topic links and example tabs are native controls in document order;
  no custom key handling was introduced. IME, drag, and pointer gestures are not applicable.
- Security: pass — no new content sink. Example source is read from repository files at build time,
  never from user input, and the prohibition on raw HTML, dynamic code and remote modules is
  unchanged and still enforced.
- Performance: pass — measured island chunk and route payload recorded with scenario and
  environment.
- Theming, RTL and i18n: pass — nested navigation mirrors under RTL and inherits density and theme
  from the shell; the stage adds no message catalogue.
- SSR, hydration and RSC: pass — routes, layouts, content modules and the shell stay server
  components; client code is limited to the two shell islands, the example frame, and example
  modules, which the validator now enforces by path.
- Documentation and integration: pass — the documentation host documents itself, and the docs index
  endpoint now publishes topic routes alongside component routes.

## Decisions, debt, and blockers

- The `F0.18` boundary assertion was generalised under ADR-024 so a governed stage can be inserted
  after it; its intent, that F0.18 follows `1.02` and no public component precedes `1.03`, is
  preserved and tested.
- Icon remains the single `pendingCoverage` entry. Its content was migrated to topics without
  claiming feature coverage it does not have.
- Firefox and WebKit baselines for the two documentation visual cases remain missing, as they were
  before this stage; they clear with Phase 0 re-certification on the CI platform.
- No ADR, dependency, migration, or security exception beyond ADR-024 is outstanding.

## Boundary audit

No public component, token, or supported API changed. No per-example theme, density or direction
switcher, props playground, search, versioned documentation, or analytics was built. `1.03 SVGIcon`
remains `not-started` and no part of it was implemented. Icon's parity and coverage debts were left
to its own governed revalidation rather than being quietly closed here.
